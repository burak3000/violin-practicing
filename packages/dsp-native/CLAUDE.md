# packages/dsp-native — CLAUDE.md

Shared, platform-agnostic C++ DSP core for the violin practice project. See
the root `CLAUDE.md` for full product context and
`temp/PLAN-violin-practice-app.md` for the phased implementation plan —
this file documents this package only.

## Status (Phase 1 complete)

Phase 0 left this as an empty CMake stub. Phase 1 (see the plan's Phase 1
section) implemented the real pitch-detection core and its validation
harness:

- **YIN** and **MPM (McLeod Pitch Method)** pitch detectors, implemented as
  genuine co-equal candidates behind one shared interface, per the plan's
  explicit instruction not to let either win by default.
- A note-onset/duration segmentation layer (RMS silence gate + energy-rise +
  pitch-stability confirmation).
- A harmonicity/HNR confidence signal for suppressing pitch output on bow
  noise / scratchy attacks.
- A CTest-driven validation harness comparing both algorithms on synthetic
  fixtures (exact ground truth) and real University-of-Iowa violin
  recordings (plausibility/stability).
- **Empirical decision: YIN is the primary algorithm.** Full numbers and
  reasoning: `RESULTS.md` in this directory (this file is the technical
  reference; that one is the decision record — read it for _why_).
- **Phase 8 follow-on:** this package now also supplies the checked-in YIN
  reference CSV snapshots (`test/reference/`) that `packages/dsp-ts`'s
  conformance suite reads when verifying the shared TS port still matches
  this C++ implementation on the exact same fixture WAVs. The C++ code
  itself was not changed for that workstream.

**Explicitly not done in Phase 1** (per the plan's scope — later phases):
no audio capture/mic input, no Node addon / WASM / TurboModule platform
binding, no UI. Everything here runs from the command line against WAV
files only.

**Pending, not skipped:** a fixtures tier for the user's own HVPV-30
electro-violin (piezo pickup) recordings is wired up and documented but
deliberately empty — see "Fixtures" below and `RESULTS.md`'s closing
section for why this matters to the algorithm decision specifically.

### The shared interface (`types.h`)

Both `YinDetector` and `MpmDetector` take a `PitchDetectorConfig`
(sample rate, min/max search frequency, per-algorithm threshold) and expose
one method: `PitchResult Detect(const float* samples, size_t numSamples)`.
`PitchResult` carries `voiced`, `frequencyHz`, `confidence`, and
`periodSamples` (sub-sample-interpolated lag, useful as the `periodSamples`
input to `ComputeHarmonicity`). **`confidence` is not numerically
comparable between the two algorithms** — YIN reports `1 - CMNDF` at the
chosen lag, MPM reports the raw NSDF peak height; both are 0..1 with higher
= better, but the two quantities mean different things. Don't threshold
them against the same cutoff without re-validating.

`PitchDetectorConfig::ForViolin(sampleRateHz)` gives the validated
defaults: search range 150-1600Hz (covers G3~196Hz to ~~D6~~1175Hz with
margin), YIN threshold 0.15, MPM clarity threshold 0.93. These came from
the papers' own recommended defaults, not from tuning against this
project's fixtures — Phase 1 validated that they work well (see
`RESULTS.md`), it didn't grid-search them. Revisit if a future phase's
real-world testing suggests otherwise.

`PitchDetectorConfig::MinRecommendedFrameSize()` returns `3 * tauMax`
(tauMax derived from `minFrequencyHz`) — the smallest analysis frame that
gives ~2 full periods of the lowest searched frequency inside the
difference/NSDF integration window. At the violin defaults this is 882
samples (`3 * ceil(44100/150)`); the harness uses 2048-sample frames, well
above this floor, matching the plan's "~2048-4096 sample analysis window"
target.

### Algorithms

**YIN** (`yin_detector.h/.cpp`) — de Cheveigné & Kawahara, 2002.
Autocorrelation-style difference function -> cumulative mean normalization
-> first dip below an absolute threshold (descended to its local minimum)
-> parabolic interpolation. Reports unvoiced (but still fills in a
best-effort frequency/confidence) if nothing clears the threshold anywhere
in the search range.

**MPM** (`mpm_detector.h/.cpp`) — McLeod & Wyvill, "A Smarter Way to Find
Pitch", 2005. Normalized square difference function (NSDF) -> key-maxima
peak picking (the local max within each positive-to-negative NSDF lobe) ->
pick the _first_ (lowest-lag) peak clearing `mpmClarityThreshold *
globalMaxPeak` -> parabolic interpolation. This "first qualifying peak, not
the tallest" rule is specifically what's supposed to resist octave-down
errors when a harmonic's peak is taller than the fundamental's — see
`RESULTS.md` for why this didn't translate into fewer octave errors on real
recordings in this project's testing.

Both use **direct time-domain computation, not FFT-based autocorrelation**.
This is a deliberate simplification, not a placeholder: the violin's
practical pitch range bounds the lag search to roughly 27-294 samples
(`tauMin`/`tauMax` at the default config), so a direct O(numSamples *
lagRange) computation is already sub-millisecond (see `RESULTS.md`'s
timing table) — an FFT would add complexity and a dependency for no
measured benefit at this problem size. Revisit only if a future platform
integration's frame size grows much larger than ~4096 samples.

Both detectors are **not thread-safe** (each owns a reused scratch buffer)
— construct one instance per analysis thread.

### Harmonicity / confidence gate (`harmonicity.h/.cpp`)

`ComputeHarmonicity(samples, numSamples, periodSamples)` computes the
harmonic-to-noise ratio in dB from the normalized periodicity at a _given_
candidate period (typically whatever a detector just reported), using the
classic autocorrelation-based HNR formula (Boersma 1993):
`HNR(dB) = 10*log10(r / (1-r))`, where `r` is the same NSDF-style
normalized periodicity MPM computes internally, recomputed standalone here
so it works regardless of which detector supplied the period. This is the
"confidence/harmonicity signal usable to suppress pitch output on bow
noise / scratchy attacks" the plan called for: a detector can report a
confident-looking frequency on a noisy attack transient, but if HNR at that
period is low (periodic energy doesn't dominate), the frame should be
treated as unvoiced. The validation harness uses a 0dB gate (periodic
energy >= noise energy) — see `RESULTS.md` for how much this changes the
real-recording numbers (a few percentage points, not a qualitative
difference).

### Onset/duration segmentation (`onset_detector.h/.cpp`)

`OnsetSegmenter` is a small stateful stream processor: feed it one frame's
RMS (dBFS, from `ComputeRmsDbfs`) and gated pitch (voiced + frequency) per
hop, in order. It implements exactly what the plan asked for and nothing
more:

1. **Silence/noise gate**: RMS at or below `silenceThresholdDbfs` (default
   -50dBFS, configurable) forces `kSilence` regardless of what the pitch
   detector said.
2. **Onset via energy rise**: leaving silence, or a `>= onsetRiseDb`
   (default 6dB) frame-to-frame RMS jump while already in a sustained note
   (a slurred note change with no gap), opens an `kAttack` window.
3. **Pitch-stability confirmation**: `kAttack` is promoted to `kSustained`
   (the actual "note onset" event) only once `stabilityConfirmFrames`
   (default 3) consecutive voiced frames all fall within
   `stabilityCentsTolerance` (default 35 cents) of their own mean — this is
   what prevents a bow-attack transient's noisy first frame(s) from being
   reported as the note's pitch.

**Deliberately NOT spectral-flux based** — the plan rejected that as
unneeded compute for this monophonic bowed-string case; RMS envelope plus
the pitch stream the detectors already compute is enough signal, and it's
essentially free (see `RESULTS.md`: onset segmentation added no measurable
overhead — timing numbers there are the pitch detectors alone). Validated
in the harness against all 68 synthetic fixtures (100% detected exactly one
onset, matching each fixture's single designed tone) and against all 6 real
Iowa recordings (produces a plausible number of onsets per chromatic run,
with per-segment stability reported in `RESULTS.md`).

## Commands

From the repo root:

- `pnpm build:dsp-native` — configure + build (Release by default; the
  CMakeLists sets this unless you pass `-DCMAKE_BUILD_TYPE=Debug`
  yourself). Timing numbers are meaningless in a Debug build — always
  measure from a Release one.
- `pnpm test:dsp-native` — runs both CTest tests:
  1. `generate_synthetic_fixtures` — regenerates
     `test/fixtures/synthetic/*.wav` + `manifest.csv` fresh every run
     (deterministic; registered as a CTest `FIXTURES_SETUP` so it always
     runs before the comparison).
  2. `dsp_native_validation_harness` — the actual YIN-vs-MPM comparison.
     Writes `test/results/{synthetic,iowa,user_violin,timing}_results.csv`
     - `test/results/summary.txt`, and prints the same summary to stdout
       (visible via `ctest --output-on-failure`, or always with `-V`).
       **Fails the test** (nonzero exit) only on genuine breakage — a fixture
       failing to load, or clean-sine-tone accuracy/octave-error sanity
       thresholds being blown — never merely because one algorithm
       underperforms the other (that's the bake-off's expected, legitimate
       output, not a regression).
       The current YIN rows from `test/results/{synthetic,iowa}_results.csv`
       are also what gets copied into `test/reference/` when Phase 8's
       shared-port conformance baseline needs refreshing.

Or directly, from this directory: `cmake -S . -B build && cmake --build
build && ctest --test-dir build --output-on-failure`.

Both executables also run standalone outside CTest:
`./build/generate_synthetic_fixtures test/fixtures/synthetic` and
`./build/dsp_native_validation_harness test` (paths relative to this
directory) — useful if you want stdout without CTest's own wrapping, or to
point the harness at a different fixtures root.

## Fixtures

Three tiers, per the plan's Phase 1 scope:

1. **Synthetic** (`test/fixtures/synthetic/`, regenerated by
   `generate_synthetic_fixtures`, deterministic — **checked in as of Phase 8**,
   see the file-layout table above for why): a chromatic sweep from G3 to D6, sine
   and sawtooth, one file per note per waveform (32 notes x 2 = 64 files),
   plus 4 "adversarial weak-fundamental" sawtooth files (A4, E5, A5, D6)
   with the fundamental deliberately attenuated below its own 2nd harmonic
   — a direct synthetic test of the "piezo pickups emphasize upper
   harmonics" hypothesis from the plan's citations. Every fixture is
   silence -> fade-in -> ~1.0s steady tone -> fade-out -> silence, so the
   same files exercise `OnsetSegmenter` too, not just raw pitch accuracy.
   Ground truth (exact, since it's synthesized) lives in
   `manifest.csv` next to the WAVs — the harness never re-derives it from
   filenames for this tier.

   **To add more synthetic cases:** edit
   `test/generate_synthetic_fixtures.cpp` — add MIDI numbers to the
   chromatic loop's range, add entries to the `adversarialNotes` vector, or
   add a new waveform-generator function following `SineCarrier`/
   `SawtoothCarrier`'s pattern (full-duration carrier at constant
   amplitude; envelope applied afterward via `ApplyEnvelope` so phase stays
   continuous through the fades). No changes needed in the harness itself
   — it reads whatever `manifest.csv` says.

2. **Real (University of Iowa)** (`test/fixtures/iowa/`, checked in): six
   real acoustic violin recordings covering all four strings plus a soft
   dynamic and an extreme-high-register case. Full provenance, exact
   source URLs, and the AIFF->WAV conversion command:
   `test/fixtures/iowa/README.md`. No exact ground truth (these are
   chromatic runs, not single held notes) — the harness parses a coarse
   note-range from the filename instead (`ExtractNoteRangeFromFilename` in
   `validation_harness.cpp`) and measures plausibility (in-range rate,
   octave-error rate) and stability (within-detected-note pitch std-dev)
   rather than exact cents error.

   **To add more real fixtures:** drop a `.wav` file into
   `test/fixtures/iowa/` (convert non-WAV sources the same way — see that
   README) and re-run `pnpm test:dsp-native`; no code changes needed as
   long as the filename contains a recognizable note or note-range token
   (see `test/fixtures/user-violin/README.md`'s naming section for the
   exact pattern the parser accepts — same parser, same rules, both tiers).

3. **User's own violin** (`test/fixtures/user-violin/`) — **pending, empty
   by design**. Full explanation of what to record, expected file
   format/naming, and why this specific tier matters to the algorithm
   decision: `test/fixtures/user-violin/README.md`. The harness already
   handles this tier automatically (scans the directory every run, reports
   `PENDING: 0 .wav files found` when empty rather than skipping silently)
   — dropping files in and re-running `pnpm test:dsp-native` is the entire
   "how to re-run" story, nothing else changes.

## Numbers (see `RESULTS.md` for full detail and the decision)

From the Phase 1 validation run (2048-sample frames, 512-sample hop,
44.1kHz):

- **Accuracy (synthetic, exact ground truth):** both algorithms track
  clean sine/sawtooth tones across the full G3-D6 range to a fraction of a
  cent (YIN mean 0.13c sine / 0.65c sawtooth; MPM 0.01c sine / 0.63c
  sawtooth) — both far below the ~5-cent perceptual threshold. Zero octave
  errors for either algorithm on all 68 synthetic fixtures, including the
  adversarial weak-fundamental set.
- **Accuracy (real Iowa recordings, plausibility-based):** YIN voiced
  47.6% of frames vs. MPM 38.9%; in-range-of-voiced near-tied (91.0% vs.
  91.1%); octave-error-of-voiced YIN 1.78% vs. MPM 2.61%; within-note pitch
  stability YIN 20.66c vs. MPM 91.16c aggregate std-dev (up to ~50x
  difference on the worst individual file).
- **Latency:** YIN mean 510.7us/frame (median 501.0us, p99 609.3us); MPM
  mean 523.7us/frame (median 512.9us, p99 629.1us) — both ~4.4% of the
  11.6ms hop budget at these settings, an order of magnitude of headroom
  to spare.
- **Decision: YIN is primary.** MPM stays implemented and available (not
  deleted) but is not run as an always-on cross-check — its hypothesized
  octave-error-resistance advantage did not materialize on real recordings
  in this testing. Full reasoning and the "what would change this"
  condition (user's own piezo-pickup recordings, still pending):
  `RESULTS.md`.
