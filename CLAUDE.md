## What this app is

A cross-platform desktop + mobile app that listens to the user's electro-violin over an audio input and scores how accurately their fingers land on pitch, in real time. Source of truth for requirements is the user's mind map (outside this repo); the summary below is derived from it.

Two required modes:

- **Finger Tuner** — continuous real-time pitch/intonation feedback on whatever note is currently being played.
- **Playing Practice** — the app shows a target note, the user plays it, the app scores that single note. On success it advances to the next note in the sequence; on failure it enters a **Drilling** submode that repeats that note plus its immediate neighbors until mastered.

Pitch detection is **monophonic** (one note at a time) — chords/double-stops are explicitly out of scope.

## Hardware reality (drives the audio pipeline)

The violin's onboard preamp outputs a plain **analog** signal via a 1/4" (6.35mm) LINE OUT jack (HVPV-30-style unit: Volume/Tone knobs, separate Mic/Phone jacks, on/off switch/LED). There is no MIDI, no USB, no digital pitch data — pitch and note duration must be derived entirely from the raw audio waveform in software. On mobile this implies an external audio interface/adapter dependency (phones rarely expose a 1/4" or even 3.5mm input) — treat this as a real UX constraint, not an edge case.

## Priorities, in order

1. **Pitch/duration detection correctness.** This is the single most important property of the app. Decisions about detection algorithms/libraries should be backed by actual research/comparison, not the first thing that works.
2. **Performance** — right after correctness, except correctness wins whenever the two conflict. If a feature choice creates a genuine performance tradeoff, surface it for the user to decide rather than resolving it silently. Prefer techniques like lazy loading and eager/upfront loading at app boot (a longer boot time is acceptable if it keeps the actual practicing loop fast).

## Constraints

- **Single monorepo** covering both targets — never split desktop/mobile into separate repos.
- **Desktop**: cross-platform Electron.js app (Electron Forge, Vite + TypeScript template).
- **Mobile**: Expo (React Native), **New Architecture enabled from the start** — confirmed, non-negotiable decision (see `temp/PLAN-violin-practice-app.md`'s "Confirmed architectural decisions"). Primary mic-capture path, **installed and wired as of Phase 4**: `react-native-audio-api`, requiring a custom dev client (Expo Go can't load it — `expo-dev-client` is now a real dependency). Conditional fallback if that path's go/no-go checkpoint fails on a real device: a Tuneo-style native TurboModule (plan's Phase 4b, not started — see `apps/mobile/CLAUDE.md`).
- Share core logic/components between desktop and mobile **where it doesn't hurt performance**; when sharing and performance conflict, platform-specific implementation wins.

## CI and releases (GitHub Actions)

Two workflows in `.github/workflows/`, following the conventions of the owner's other repos (`vX.Y.Z` tags, tag-must-be-on-`main`, package-version-must-match-tag, `gh release create --verify-tag --generate-notes`):

- **`ci.yml`** — on every push to `main` and every pull request. Three independent jobs: `checks` (ubuntu: `format:check`, `lint`, `typecheck`, `test`), `dsp-native` (ubuntu: CMake build + the CTest validation harness — the only place the C++ reference is compiled with gcc rather than macOS clang), and `desktop-windows` (windows: a full `electron-forge make`, uploading the installer as a 7-day workflow artifact, so every green `main` commit has a downloadable Windows build even without a release).
- **`release.yml`** — on a `v*` tag. `validate` (tag format, tag on `main`, tag == `apps/desktop/package.json` version, typecheck, tests) → `build` matrix (windows + macos, `pnpm --filter @violin/desktop run make`) → `publish` (GitHub release with install notes). Running it manually (`workflow_dispatch`) is a **dry run**: it builds and uploads every installer as a workflow artifact but publishes nothing.

**To cut a release:** bump `version` in `apps/desktop/package.json` (the single version the release validates against — the root `package.json` version is unused), commit, push `main`, then `git tag vX.Y.Z && git push origin vX.Y.Z`.

Release artifacts: Windows gets `ViolinPractice-Setup.exe` (Squirrel, per-user, no admin) plus a portable `win32` zip; macOS gets a zip of the `.app`. **Nothing is code-signed or notarized** — Windows SmartScreen warns on first run ("More info → Run anyway") and macOS needs `xattr -cr "Violin Practice.app"`; the release notes say so. Mobile is not built in CI (it needs a native Xcode/Gradle toolchain and a custom dev client); only its typecheck and unit tests run.

Things that exist specifically so the Windows build works — don't "clean up" without reading why:

- **`pnpm-workspace.yaml` allows `electron-winstaller`'s install script.** It copies the host-arch 7-Zip to `vendor/7z.exe`, which the Squirrel maker needs. It was declined through Phase 8 (nothing built for Windows then). Note pnpm only runs it on a _fresh_ install — `pnpm rebuild` is a silent no-op under `nodeLinker: hoisted`, and a plain `pnpm install` short-circuits on pnpm 11's workspace-state check — so verify changes here with a clean `node_modules`, as CI does.
- **`pnpm-workspace.yaml` also needs `electron: true` in `allowBuilds`, counter-intuitively.** `electron@44.2.0` declares no lifecycle scripts in its registry manifest, yet pnpm 11 still reports it as an ignored build and **fails the install** (`ERR_PNPM_IGNORED_BUILDS`) without an explicit decision — then writes a placeholder line into the workspace file, leaving it invalid. Why pnpm flags it is not understood. Removing the entry because "Electron 44 has no install scripts" was tried while building this pipeline and broke `pnpm install`; see the comment in that file. Relatedly: a clean install has no `node_modules/electron/dist` until Electron is first run (it downloads on demand) — that's expected, not a broken install.
- **`forge.config.ts` sets the Squirrel maker's `name` explicitly** (`violin_practice`). It defaults to `package.json`'s `name`, and `@violin/desktop` is not a legal NuGet package id.
- **`main.ts` opens DevTools only when `!app.isPackaged`**, so the installed app doesn't launch with DevTools open.
- Workflows pin **Node 22** (the local toolchain is newer; `engines` allows `>=20`) and take the pnpm version from `package.json`'s `packageManager` field.

Notable Phase 0 tooling decisions (see inline comments in the referenced files for the full reasoning — flagged here so they aren't accidentally "fixed" or second-guessed later):

- **TypeScript pinned to `~6.0.3` repo-wide** (root, `apps/desktop`, `packages/core`; `apps/mobile`'s Expo template already pinned there independently). `typescript-eslint@8.69.0`'s peer range caps at `<6.1.0`; TypeScript 7.x (npm's `latest` at scaffold time) isn't yet supported by that tooling.
- **ESLint uses `typescript-eslint`'s non-type-checked `recommended` preset**, not `recommendedTypeChecked` — a single `parserOptions.project` can't cleanly span `apps/mobile`'s Metro tsconfig, `apps/desktop`'s Vite/Node tsconfig, and `packages/core`'s Vitest tsconfig at once. Revisit per-package if type-aware lint rules become worth the extra wiring.
- **`pnpm-workspace.yaml` sets `nodeLinker: hoisted`** — Electron Forge's packaging step (`electron-forge package`/`make`) requires a hoisted, npm/yarn-style `node_modules` layout and fails its own preflight check against pnpm's default symlinked virtual store.
- **`pnpm-workspace.yaml` overrides `@electron/node-gyp`** to the published npm build (`10.2.0-electron.2`) — `@electron-forge/cli` → `@electron/rebuild` normally pins it to a raw git commit, which pnpm blocks by default as a git-resolved subdependency (`blockExoticSubdeps`). Only matters when rebuilding native Node addons, which Phase 0 doesn't do.
- **`apps/desktop` explicitly depends on `@electron-forge/shared-types`** (used by `forge.config.ts`) rather than relying on it being hoisted — pnpm's strict `node_modules` doesn't expose transitive-only packages the way npm/yarn's flatter layout does.

Notable Phase 4 tooling decisions (same flagging purpose as above — see the referenced files/`apps/mobile/CLAUDE.md` for the full reasoning):

- **`apps/mobile/metro.config.js` overrides Metro's module resolution** to retry a failed relative `./x.js`/`.jsx` import (TypeScript `NodeNext`-style, used by `packages/core` and `packages/dsp-ts`) without the extension, falling back to Metro's normal `.ts`/`.tsx` search. Metro doesn't do this by default (unlike `tsc` and Vite/esbuild, which both already handled it fine for `apps/desktop`). This didn't matter before Phase 4 because `apps/mobile` never imported either shared package until now — don't assume it's dead/unnecessary config later just because it's not obviously exercised by whatever you're looking at.
- **`apps/mobile` depends on `react-native-gesture-handler` and `react-native-reanimated`** despite never importing either directly — `react-native-audio-api`'s own top-level barrel unconditionally re-exports a playback-UI component (`AudioControls`) that needs both, and neither is declared as a peer dependency in that library's `package.json` (looks like a real upstream packaging gap, not a mistake here). Required for Metro to bundle at all; see `apps/mobile/CLAUDE.md`'s "A real upstream gap" section before assuming these are unused and removing them.
- **`eslint.config.mjs` has a `no-require-imports` override scoped to `apps/mobile/metro.config.js`** (and `babel.config.js`, if one is added later) — Metro/Babel config files are CommonJS by the tooling's own convention and can't be ESM like every other config file in this repo.

Notable Phase 5 tooling decision (same flagging purpose as above):

- **`apps/mobile/vitest.config.mts` is named `.mts`, not `.ts`** like `packages/core`/`packages/dsp-ts`'s own `vitest.config.ts` files — this app's own `test`/`test:watch` scripts are new in Phase 5 Part B (see `apps/mobile/CLAUDE.md`'s "Notable Phase 5 tooling decision" section for the full reasoning). `packages/core`/`packages/dsp-ts` both have `"type": "module"` in their `package.json`, so their `.ts` config files are already unambiguously ESM to Node/Vite; `apps/mobile`'s `package.json` cannot safely add `"type": "module"` without breaking `metro.config.js`'s CommonJS `require()`-based loading (see the Phase 4 bullet above). `.mts` is an explicit ES-module extension that sidesteps the question entirely without touching `package.json`.
