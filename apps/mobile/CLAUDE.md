## DSP hosting: event callback, not a worklet

The plan's own Phase 4 scope explicitly poses this as a decision to make in this phase: "integrate the mic stream with [the DSP pipeline] running as an audio-thread worklet if the library's worklet system supports it, otherwise via its standard event-based buffer delivery." This section documents that decision, mirroring how `apps/desktop/CLAUDE.md`'s "DSP binding decision" section documents Phase 3's analogous call — reasoned and flagged per Hard Rule 3, not a silent default, and **reversible**.

**What `react-native-audio-api` 0.13.3 actually offers, verified from its real source/types (`node_modules/react-native-audio-api/lib/typescript/**`, `node_modules/react-native-audio-api/src/hooks/useAudioInput.ts`), not assumed from its published docs (which turned out to be incomplete on more than one point this phase — see "External audio interface" below for the most striking example):**

- `AudioRecorder.onAudioReady(options, callback)` — an **event-based callback on the JS thread**, fed by the native recorder. Simple, well-documented, used in the library's own complete example.
- `AudioContext.createWorkletProcessingNode(worklet, workletRuntime)` / `WorkletSourceNode` — a genuine **audio-thread worklet system**, JS-on-the-audio-thread via the separate `react-native-worklets` package (peer dependency, `>= 0.6.0`, marked `optional` in `react-native-audio-api`'s own `package.json`). The worklet callback signature is `(inputData: Float32Array[], outputData: Float32Array[], framesToProcess: number, currentTime: number) => void`, framesToProcess capped at 128 per call (mirroring Web Audio's own render quantum) — directly analogous in shape to `apps/desktop`'s `AudioWorkletProcessor.process()`.

**Decision: event callback (`onAudioReady`), not the worklet path — for this phase.** Reasoning:

1. **A real, unverifiable-here uncertainty about hosting `PitchAnalysisPipeline` inside a `react-native-worklets` worklet.** `PitchAnalysisPipeline` is not a simple pure function — it owns a `YinDetector` + `OnsetSegmenter` + `ClipDetector`, each with mutable per-frame state (a reused scratch buffer, a rolling recent-pitch window, a consecutive-hot-frames counter), constructed **once** and reused across thousands of calls. `react-native-worklets`' worklet functions run under a closure-serialization model (values referenced by a `'worklet'`-tagged function are captured/transferred to the worklet's own JS runtime) that is well-proven for simple values and plain functions (as in every published example, including this library's own gain-effect worklet), but whether a **whole class-instance object graph with internal mutable state**, constructed on the main JS thread and expected to keep accumulating state correctly across many separate invocations _on the worklet thread_, behaves identically under that model is not something this phase's documentation or source reading resolved with confidence — and it is exactly the kind of thing that would need a real device/simulator run to actually verify, which this phase is explicitly barred from attempting (see the top-level task's Hard Rules).
2. **The plan itself names the event-based path as the explicit fallback for exactly this situation** ("otherwise via its standard event-based buffer delivery") — this isn't a workaround invented under time pressure, it's the documented alternative the plan already anticipated needing.
3. **Avoiding an unverified new dependency.** Taking the worklet path would add `react-native-worklets` as a real, load-bearing dependency (not just an incidentally-present transitive one — see the note at the end of this section) whose correctness for this specific use case this phase cannot check. `HopBuffer` (from `packages/dsp-ts`) was written from Phase 3 onward to accept _any_ input block size, specifically so it would be reusable unchanged regardless of which delivery mechanism a future platform used — this made the event-callback path a genuinely mechanical integration, not a compromise requiring new code.
4. **This is reversible, not permanent**, exactly like Phase 3's WASM-vs-TS-port call: if a real device/simulator run (the orchestrator's or the user's next step) shows the event-callback path's JS-thread scheduling is too jittery for the go/no-go latency checkpoint, switching `mic-capture-controller.ts` to construct a `WorkletProcessingNode` instead is a contained, scoped follow-up — `packages/dsp-ts`'s pipeline code itself would need zero changes either way, only the glue that drives it.

**Incidental, not deliberate**: installing `react-native-reanimated` (needed for an unrelated reason — see "A real upstream gap" below) pulled in `react-native-worklets` as _reanimated's own_ transitive dependency, so it is now present in `node_modules` despite this app never importing or using it directly. This doesn't change the decision above; `mic-capture-controller.ts` has no reference to it.

## External audio interface

Root `CLAUDE.md`'s hardware-reality section is explicit: modern phones rarely have a built-in line/instrument input, an external USB-C/Lightning class-compliant audio interface is the practical path for the HVPV-30, and "the app should detect available audio input routes and clearly prompt the user to select the interface rather than silently defaulting to the built-in mic."

**This phase's research process is worth documenting because it produced a materially wrong first answer.** A web-doc fetch of this library's published documentation stated, in effect, "no explicit input device selection method is documented; routing appears automatic." Rather than accepting that as final, the actual installed package's own TypeScript source was read directly (`node_modules/react-native-audio-api/lib/typescript/system/AudioManager.d.ts` and `.../hooks/useAudioInput.ts`) — and it turned out the published docs were **incomplete**, not the library:

- **`AudioManager.setInputDevice(deviceId: string): Promise<void>`** genuinely exists and is exported.
- **`useAudioInput()`** is a ready-made, first-party React hook (`import { useAudioInput } from 'react-native-audio-api'`) returning `{ availableInputs, currentInput, onSelectInput }`, auto-updating on OS route-change events. `App.tsx` uses this hook directly rather than re-deriving equivalent logic.
- **The hook's own doc comment is explicit and load-bearing: "(iOS only currently)."** Reading its actual implementation (`node_modules/react-native-audio-api/src/hooks/useAudioInput.ts`) confirms this isn't hedging — `onSelectInput` calls `AudioManager.setInputDevice(device.id)` unconditionally on both platforms, so what "iOS only" means in practice is that Android's native implementation doesn't yet honor the request the same way (untested here — no device). `App.tsx` handles this by showing a platform-appropriate message if `onSelectInput` rejects on Android, rather than presenting a control that silently does nothing.

**Net result, stated precisely rather than optimistically:**

- **iOS**: real, explicit input-device selection is available (`availableInputs` enumerated, tap-to-select via `onSelectInput`, `currentInput` reflected in the UI) — this fully satisfies the plan's requirement on this platform, pending real-device confirmation that selecting a connected USB/Lightning interface actually routes audio from it (not verified — no device).
- **Android**: only read-only enumeration (`availableInputs`) plus OS-automatic routing is currently available through this library; explicit selection is not yet supported by its own admission. The debug UI still surfaces whatever the OS reports (satisfying the "detect and display, don't silently default to the built-in mic" half of the requirement) but cannot fulfill the "let the user choose" half on Android with this library version. **Flagged as a real, currently-unresolved platform gap** against the plan's explicit requirement — not silently worked around, not silently ignored. Options if this matters before Android's own support lands upstream: pin and re-check on every `react-native-audio-api` upgrade (the plan already calls for re-validating the go/no-go checkpoint on any upgrade of this "actively-developing library"), or treat it as one more data point toward the Phase 4b native-TurboModule fallback if Android's own checkpoint fails for a related reason.

## Known correctness gap: Android AGC / noise suppression

Root `CLAUDE.md`'s priority #1 is pitch-detection correctness. On desktop, this is why `capture-pipeline.ts` explicitly sets `echoCancellation`/`noiseSuppression`/`autoGainControl` all to `false` in its `getUserMedia` constraints — these are designed to suppress non-voice, pure-tone-like signal and would actively hurt pitch detection if left on. On iOS, `MicCaptureController.configureSession()` sets `iosMode: 'measurement'` specifically because Apple documents that `AVAudioSession` mode as minimizing the system's own signal processing — the closest available native equivalent.

**No equivalent Android-side control was found** anywhere in `react-native-audio-api` 0.13.3's documented or type-declared `AudioManager`/`AudioRecorder` surface during this phase's research (grepped the library's actual source for every external import and read every relevant `.d.ts` file directly — no `audioSource` option, no AGC/NS toggle of any kind). This matters concretely: Android's `MediaRecorder.AudioSource` concept has well-known values (`UNPROCESSED`, `VOICE_RECOGNITION`) specifically for minimizing platform-applied AGC/noise-suppression, and other, less-Web-Audio-API-shaped React Native audio libraries (e.g. `react-native-audio-record`) do expose this — this one, as far as this phase's research found, does not (yet). Since Android phones commonly apply aggressive platform AGC/NS by default with no way to disable it through this library today, **this is a real, currently-unresolved correctness risk specific to Android**, not an oversight in this app's code. It cannot be verified or worked around without either a real Android device (to see how bad it actually is in practice — it may be a non-issue, or it may meaningfully distort pitch tracking) or a newer library version that exposes such a control. Flagged here explicitly per this project's "pitch-detection correctness is priority #1" stance, for the orchestrator/user to weigh when running the real-device checkpoint — this is exactly the kind of finding the go/no-go checkpoint exists to surface.

## Metro + NodeNext `.js` imports (read before touching `metro.config.js`)

`packages/core` and `packages/dsp-ts` both use TypeScript's `NodeNext`-style relative imports (`import ... from './clamp.js'` inside a file that is actually `clamp.ts`), required by their own `tsconfig.json`'s `moduleResolution: "NodeNext"`. Both `tsc` itself and `apps/desktop`'s Vite/esbuild-based bundler already handle this convention correctly (esbuild maps an explicit `.js` specifier back to the sibling `.ts` source). **Metro does not, by default.**

This was discovered during this phase, not before, because **`apps/mobile` is the first Metro-bundled target in this repo to ever import `packages/core` (or now `packages/dsp-ts`) at all** — Phase 0 through Phase 3 never wired either package into this app (see this file's own Phase 0 history and root `CLAUDE.md`'s "as of Phase 3, `apps/desktop` is its first real consumer... `apps/mobile` still doesn't import it" note). The very first `npx expo export --platform all` run in this phase failed with `Unable to resolve module ./clamp.js from packages/core/src/index.ts` — a latent incompatibility between two already-existing, already-validated packages and this app's bundler, not a bug introduced by `react-native-audio-api` or any of this phase's own new code.

**Fix, in `metro.config.js`** (this app had no Metro config file before this phase — Phase 0 never needed one): a custom `resolver.resolveRequest` that, only when Metro's own default resolution already failed for a relative `./x.js`/`.jsx` import, retries once with the extension stripped, letting Metro's normal `sourceExts` search (which includes `ts`/`tsx`) find `./x.ts` instead. Scoped narrowly — the fallback only ever runs after the default resolver has already thrown, so every import that resolves normally (including any working literal `.js` file) is completely unaffected. See the file's own extensive comment for the full reasoning. Verified by re-running `npx expo export --platform all` after adding it: the `clamp.js` error was gone (a different, unrelated error appeared next — see "A real upstream gap" below), confirming the fix actually works rather than just plausibly should.

An ESLint override was added (`eslint.config.mjs`) to allow this file's necessary `require()` (Metro loads its config via CommonJS `require`, so it can't be an ESM `import` the way every other config file in this repo is) — the first plain-CommonJS config file in an otherwise TS/ESM-first repo.

## A real upstream gap: `react-native-audio-api`'s barrel pulls in undeclared peer dependencies

After fixing the Metro/NodeNext issue above, `expo export` hit a second, unrelated failure: `Unable to resolve module react-native-gesture-handler from node_modules/react-native-audio-api/src/Audio/controls/AudioControls.tsx`. Investigating (`grep`-ing every external import across the library's actual source) found the full picture:

- `react-native-audio-api`'s top-level barrel (`src/api.ts` -> `lib/typescript/index.d.ts`) unconditionally re-exports `AudioControls`, a ready-made playback-scrubber UI component this app never imports or renders anywhere.
- `AudioControls.tsx` imports `react-native-gesture-handler` and `react-native-reanimated`.
- **Neither is declared as a peer dependency** in `react-native-audio-api`'s own `package.json` (only `react-native-worklets` is, and it's marked optional) — this looks like a genuine packaging gap in the library itself, not a mistake in this app's setup: Metro traverses the _entire_ module graph reachable from any `import ... from 'react-native-audio-api'` (it doesn't tree-shake unused named exports away before dependency resolution the way Vite/Rollup can), so any consumer of this library who imports even a single thing from its root (as this app does, for `AudioManager`/`AudioRecorder`) pulls in `AudioControls`'s own dependency chain whether or not they use it.

**Fix**: installed `react-native-gesture-handler` and `react-native-reanimated` via `npx expo install` (which picked the correct SDK-57-compatible versions, `~2.32.0` and `4.5.1` respectively) — both are extremely common, safe, well-established React Native libraries with no architectural implications of their own; this is a routine "complete the dependency graph" fix, not a new decision. No Babel plugin configuration was added for `react-native-reanimated` (normally needed for apps that actually author `'worklet'`-directive functions) since this app never renders `AudioControls` or otherwise uses reanimated directly — the unused component's own code never executes, so its Babel-plugin-dependent behavior is never reached. **Revisit if a future phase actually renders `AudioControls` or any other reanimated-using component from this library.** Confirmed by re-running `expo export --platform all`: both iOS and Android bundled successfully afterward (Hermes bytecode, 1113/1125 modules respectively) with no further missing-module errors.

This phase (Part B) is the mobile equivalent: replace this app's own Phase 4 debug UI with a real Finger Tuner, reusing that exact same smoothing class rather than re-deriving it. **Only the UI layer changed** — `src/audio/permissions.ts`, `src/audio/mic-capture-controller.ts`, and everything under `@violin/dsp-ts` are untouched from Phase 4.

### What it looks like

There is no DOM/CSS on this platform, so this ports the _concept_ of desktop's design — same states, same color language, same layout order — using React Native `View`/`Text`/`Pressable`/`Animated`, not a literal translation of desktop's HTML/CSS:

1. **Header** — "Finger Tuner" title, plus a small pill "Debug info" / "Hide debug info" toggle button in the top-right corner (mirrors desktop's own header exactly in role).
2. **Permission card** — shown _only_ while microphone permission isn't yet granted (the Phase 4 permission flow, carried over unchanged: platform-aware denied-state copy, an Android "try again" path, an iOS Settings deep link). Once granted, this card disappears entirely — unlike Phase 4's debug UI, which always showed a "Status: Granted" line, so the screen reads as an actual tuner once it's usable rather than a permanently-visible setup checklist.
3. **Control bar** — shown once permission is granted: the Phase 4 device list (`useAudioInput()`, tap a row to select — iOS-only for actual selection, the same real library limitation Phase 4 already documented, not a new gap) plus Start/Stop buttons and a capture status line. Visually secondary (small text, thin borders) compared to the tuner display below it, mirroring desktop's own compact toolbar role rather than Phase 4's debug-panel-style numbered sections.
4. **The tuner itself** (most of the screen's vertical space):
   - A small uppercase state-label line, visible **only** for `no-signal` ("No signal") and `unclear` ("Unclear signal (bow noise, double-stop, or background noise?)") — identical copy to desktop's own labels, for the same "feels like the same app" reason.
   - A large note name (e.g. "A4") next to a signed cents readout (e.g. "+12c") — both render as an em-dash placeholder for `no-signal`/`unclear`. **A note name is never shown for those two states** — structurally guaranteed (the note/cents `Text` nodes only ever read `smoothedReading.note`/`.cents` inside a `smoothedReading.status === 'reading'` branch — see `src/tuner/FingerTunerScreen.tsx`), not just a styling convention, mirroring desktop's own structural guarantee via `renderTuner()`'s early returns.
   - `TunerMeter` (`src/tuner/TunerMeter.tsx`) — a horizontal +/-50-cent gauge: a shaded in-tune zone (its width derived from `packages/core`'s actual `DEFAULT_IN_TUNE_CENTS_TOLERANCE` via `tuner-view-model.ts`'s `inTuneZoneBounds()`, not a hardcoded matching number), a center tick, and a needle that animates (`Animated.timing`, 80ms, matching desktop's CSS `transition: left 80ms linear`) to the smoothed cents value, fading out (150ms, same as desktop's `opacity 150ms ease`) during `no-signal`/`unclear`.
   - A small monospace frequency readout (e.g. "440.02Hz"), shown only while `reading`.
   - A "Clipping — reduce input gain" warning line, shown whenever the current hop's `clipping` flag is set, independent of tuner status — same as desktop, since clipping is an actionable signal-quality issue, not a debug-only concern.
   - **Color**: gray for `no-signal`/`unclear`, green for an in-tune `reading`, amber for "close" (out of tune but within a presentation-only band), red beyond that — the exact same 5-tone model and hex values as desktop's `index.css` (`#b8b8b8` / `#1a7f37` / `#b45309` / `#b91c1c`), computed by `tuner-view-model.ts`'s `toneFor()` / `TUNER_TONE_COLOR` rather than re-derived per component. The close/out split (`CLOSE_OUT_BOUNDARY_CENTS`) is the identical cosmetic-only midpoint desktop's `renderer.ts` uses — it does not feed back into anything `packages/core` scores.
5. **Debug panel** (collapsed by default, toggled by the header button) — everything Phase 4's debug UI used to show as the primary view: the raw (unsmoothed) reading side by side with the smoothed one (both via one shared `formatForDebug()`, since `FingerTunerReading` and `SmoothedTunerReading` are the same shape), onset state, clipping (repeated in raw form), hop compute time (last/mean), and frames analyzed. See "Why mobile's debug panel is thinner than desktop's" below for why this doesn't carry over desktop's fuller 3-metric latency panel.

Two intentional, minor simplifications versus the Phase 4 debug UI, worth naming since they're visual-design judgment calls (not functionality regressions — the underlying data is unchanged either way):

- Device rows no longer show each device's `category` string (just its `name`) — decluttering for a "real tuner" feel; the full `AudioDeviceInfo` object is still passed to `onSelectInput` unchanged.
- The explanatory paragraph about external audio interfaces being a hardware requirement (shown unconditionally in Phase 4's UI) is no longer always on screen — it now only appears as `hint` text once the device list is genuinely empty. The underlying constraint (root `CLAUDE.md`'s hardware-reality section) obviously still applies; this is purely about not permanently occupying screen space with explanatory copy once the app is already usable.

### Why mobile's debug panel is thinner than desktop's

Desktop's debug panel shows three separate latency numbers (hop compute time, worklet->main relay latency, hop arrival cadence) because its DSP runs inside a real `AudioWorkletProcessor` on a separate audio-rendering thread, so a cross-thread relay time is a real, distinct thing to measure. Mobile's DSP hosting (`mic-capture-controller.ts`'s `onAudioReady` event callback) runs entirely on the JS thread — see that file's own doc comment — so there is no separate thread to relay across, and no meaningful "arrival cadence" distinct from compute time either (both were already true in Phase 4; this phase didn't change the pipeline, only made the _display_ of this one number more prominent). `src/tuner/rolling-stats.ts`'s `RollingStats` class exists specifically because this one number (`last`/`mean`) is the only latency metric genuinely worth tracking here — see that file's own doc comment for the detailed reasoning, and `apps/desktop/src/renderer.ts`'s own fuller `RollingStats` for the desktop analogue this was deliberately trimmed from.

### Reused verbatim, not re-derived: `TunerDisplaySmoother`

`App.tsx` constructs exactly one `TunerDisplaySmoother` (`@violin/core`, default config, no overrides — same as desktop) for the app's lifetime, via `useState(() => new TunerDisplaySmoother())` (a stable instance across re-renders, per React's own lazy-initializer guarantee — see that file's inline comment for why this is used instead of `useRef(new TunerDisplaySmoother())`, which would construct-and-discard a fresh instance on every render). Per analysis hop:

```
result (MobileAnalysisResult, from MicCaptureController.onAnalysis)
  -> PitchReading                                    (unchanged from Phase 4)
  -> analyzeTunerReading(reading)          -> rawReading   (unchanged from Phase 4)
  -> smoother.update(rawReading, performance.now()) -> smoothedReading  (NEW)
  -> <FingerTunerScreen smoothedReading=... rawReading=... .../>
```

`performance.now()` is read directly inside the JS-thread `onAnalysis` callback as the smoother's timestamp source. This is actually a _simpler_ case than desktop's: desktop's worklet runs on a separate real-time audio thread and has to rely on the documented (but not spec-guaranteed) assumption that the worklet and main-thread clocks share a time origin (see `apps/desktop/CLAUDE.md`'s "Latency measurement" section); this app's event-callback DSP hosting means everything — capture delivery, DSP compute, and this timestamp read — happens on one JS thread, so there's no cross-thread assumption being made at all here.

`smoother.reset()` is called whenever `captureState.status !== 'running'` (`App.tsx`'s own `useEffect`) — mobile's `CaptureState` has no `'self-test'` state to additionally exclude the way desktop's does (this app has no self-test/synthetic-tone path), so "not running" is the complete equivalent of desktop's "every non-actively-capturing state" condition.

**No smoothing math was reimplemented or forked for mobile** — every constant (`DEFAULT_TUNER_SMOOTHING_WINDOW_MS`, `DEFAULT_TUNER_TRANSITION_THRESHOLD_CENTS`), the vibrato-averaging boxcar, and the transition-snap heuristic all come from `@violin/core` exactly as Phase 5 Part A wrote and tested them. This app's own new code (`src/tuner/tuner-view-model.ts`) only decides how to _label and color_ whatever the shared smoother already computed — see that file's own doc comment.

### New pure logic + tests (this phase's own testable surface)

Per this phase's verification requirement ("any new/changed logic gets real unit tests where it's meaningfully testable"), the display-derivation math that would otherwise have been inline JSX/component logic was extracted into plain, React-Native-import-free modules under `src/tuner/`, each with a real test file — **29 new tests across 3 new test files**, none of it re-testing anything `packages/core`/`packages/dsp-ts` already cover:

- `tuner-view-model.ts` / `.test.ts` — `toneFor()` (the 5-way no-signal/unclear/in-tune/close/out classification), `formatCents()` / `formatFrequencyHz()` / `formatForDebug()` (display formatting), `needlePercent()` and `inTuneZoneBounds()` (the meter's position/geometry math) — direct ports of `apps/desktop/src/renderer.ts`'s own equivalent helpers, reimplemented as pure functions instead of DOM mutations. Tests build realistic `SmoothedTunerReading` fixtures via the real `analyzeTunerReading` + `TunerDisplaySmoother` (mirroring `packages/core`'s own `tuner-display-smoother.test.ts` convention) rather than hand-rolling them, and check boundary conditions (the close/out split exactly at its midpoint, needle clamping beyond +/-50c, a tolerance override clamped to a sane range).
- `rolling-stats.ts` / `.test.ts` — the windowed mean tracker described above (window eviction, non-finite-value rejection, reset, an invalid constructor argument).
- `input-select-error.ts` / `.test.ts` — the Android-vs-iOS message branching for `useAudioInput()`'s `onSelectInput()` rejection, extracted from Phase 4's inline `App.tsx` catch handler so it's testable without a React Native environment or a mocked `Platform.OS` (the caller passes in the one fact this function needs as a plain boolean instead).

**Deliberately not unit-tested**, per this phase's own scope ("React Native UI component rendering itself doesn't need exhaustive tests"): `TunerMeter.tsx` and `FingerTunerScreen.tsx` themselves, and `App.tsx`'s own composition/wiring — these contain no logic beyond what the modules above already cover, plus React/React Native's own rendering, which this phase's instructions explicitly didn't ask to be exhaustively tested.

### Notable Phase 5 tooling decision: Vitest added to this app

This app had **no test runner at all before this phase** (see this file's former "No `pnpm test` yet" note under Commands, now obsolete) — there was no app-level logic worth unit-testing beyond what `packages/dsp-ts` already covered. This phase's new pure logic changed that calculus, so `vitest` was added as a devDependency (mirroring `packages/core`/`packages/dsp-ts`'s own `vitest: ^5.0.0` + `vitest.config.ts` convention exactly, via `pnpm add -D vitest --filter @violin/mobile`), plus `test` / `test:watch` scripts.

**One deviation from that convention, deliberate and documented**: this app's own config file is named `vitest.config.mts`, not `vitest.config.ts` like the other two packages. Reason: `packages/core`/`packages/dsp-ts` both have `"type": "module"` in their `package.json`, so Node/Vite already treat their `.ts` config files as ESM; `apps/mobile`'s `package.json` cannot safely add `"type": "module"` (see "Metro + NodeNext `.js` imports" above and the `metro.config.js`/`babel.config.js` CommonJS override already in `eslint.config.mjs` — Metro loads `metro.config.js` directly via Node's `require()`, which `"type": "module"` would break). `.mts` is an explicit, unambiguous ES-module file extension that sidesteps the whole question without touching `package.json` at all — see the file's own comment for the full reasoning. The `include` glob is scoped to `src/**/*.test.ts` only (not `.test.tsx`), so Vitest never has to load React/React Native/Metro's own transform pipeline — consistent with this phase's "don't exhaustively test components" scope.

## Phase 6 Part B: Playing Practice UI

This phase's job: add the second required mode alongside Finger Tuner, sharing the same live capture pipeline, **without touching Finger Tuner's own code or the capture/DSP layer underneath either** — the mobile equivalent of `apps/desktop`'s Phase 6 Part A (see `apps/desktop/CLAUDE.md`'s "Playing Practice UI (Phase 6)" section for the design this ports; read that section first, since this one assumes it). Only `src/practice/playing-practice-controller.ts` and `src/practice/PlayingPracticeScreen.tsx` (both new) plus additive changes to `App.tsx` (a mode-tabs switcher + wiring) — `src/audio/mic-capture-controller.ts`, `src/audio/permissions.ts`, `@violin/dsp-ts`, and Finger Tuner's own code (`src/tuner/FingerTunerScreen.tsx`, `TunerMeter.tsx`, `tuner-view-model.ts`, `rolling-stats.ts`, `input-select-error.ts`) are byte-for-byte what Phase 5 Part B left them.

### Why a headless controller + view-state, not a literal DOM-mutation port

Desktop's `PlayingPracticeUi` (Phase 6 Part A) directly mutates `HTMLElement`s it's handed — there is no React Native equivalent of that shape, since RN has no persistent DOM to mutate and no `hidden` attribute trick for "update it but don't show it." Instead, `src/practice/playing-practice-controller.ts`'s `PlayingPracticeController` computes a plain, serializable `PlayingPracticeViewState` snapshot (a discriminated union: `{ phase: 'config', ... }` | `{ phase: 'session', session: ... }`) and pushes it to an `onChange` callback whenever it changes — the same event-callback shape this app's `MicCaptureController` already uses, and the same "pure view-model, no RN imports, independently unit-tested" shape this app's own `src/tuner/tuner-view-model.ts` already established in Phase 5 Part B. `App.tsx` owns one instance (constructed via `useRef`, mirroring `controllerRef`'s own pattern exactly) and renders `<PlayingPracticeScreen viewState={...} .../>`, a purely presentational component with no state of its own — the same split `FingerTunerScreen.tsx`/`App.tsx` already use for Finger Tuner. This is a mechanical translation, not a re-derivation: every piece of _logic_ (config reading, preview computation, the give-up/pause/hand-off state machine driving `PracticeSessionController` + `PracticeAttemptTracker`) is a direct, verbatim-in-substance port of `apps/desktop/src/playing-practice-ui.ts`'s own methods (`readConfig`, `computePreview`/`updatePreview`, `start`, `renderCurrentState`, `applyResult`, `handleAnalysisFrame`) — only the "how does the result reach the screen" mechanism differs.

**One real, non-obvious bug found and fixed while porting `applyResult()`'s pause/success-banner logic, worth flagging for anyone touching this again**: desktop's `applyResult()` calls `this.controller.reportOutcome('success')` (which internally advances `PracticeSessionController`'s state to the _next_ note immediately) and then, for a non-final success, sets the "Nice!" banner visible and returns _without_ touching `#pp-target-note`'s DOM text — so the stale (just-completed) note's name stays on screen next to "Nice!" by simple omission, until `renderCurrentState()` actually runs again once the pause elapses. A first pass at this controller re-derived `targetNoteLabel` fresh from `sessionController.state` on every `computeViewState()` call (the natural "pure function of current state" instinct) — but since `sessionController.state` had _already_ advanced to the next note by the time the success banner was showing, this produced the wrong pairing: the banner would show "Nice!" next to the _next_ note's name, not the one just completed. Fixed by caching `currentMode`/`currentProgressText`/`currentTargetNoteLabel` as controller-owned fields, written only by `renderCurrentState()` and _read_ (not re-derived) by `computeViewState()` — the explicit equivalent of desktop's "just don't touch the DOM" omission. Caught by this phase's own test suite (`playing-practice-controller.test.ts`'s "multi-note hand-off" test), not by inspection — a concrete example of why the integration-style tests below are worth their length.

### Mode switcher

Two tabs (`ModeTab` components in `App.tsx`, `mode: 'tuner' | 'practice'` state) toggle which screen is visible; Finger Tuner stays the default active mode so its existing appearance/behavior is unchanged for anyone who never touches the new tab — mirrors `apps/desktop/index.html`'s `.mode-tabs` nav exactly in role. **Both modes share one running capture session** — there's no separate "start capture" per mode. `App.tsx`'s single `onAnalysis` callback (fed by the one live `MicCaptureController`) calls both Finger Tuner's own state-setters AND `PlayingPracticeController.handleAnalysisFrame(...)` on every hop, unconditionally, regardless of which tab is currently visible — exactly mirroring `apps/desktop/src/renderer.ts`'s `handleAnalysis()`. Unlike desktop (which achieves "both screens exist, only one is visible" via the DOM's `hidden` attribute), this app keeps **both `<ScrollView>`s permanently mounted** and toggles each one's `style` between `flex: 1` and `display: 'none'` — RN's `display: 'none'` hides an element from layout/paint without unmounting it, so React continues to re-render (and preserve local state in) both `<FingerTunerScreen>` and `<PlayingPracticeScreen>` regardless of which tab is active, matching desktop's "switching back to a tab should not have lost your place" requirement without needing any extra state-preservation logic of its own. Each `<ScrollView>` also keeps its own independent scroll position this way (a nicety desktop's single-document layout never had to consider).

### Integration point: `PracticeSessionController`, not the bare `PlayingPracticeMachine`

Identical reasoning to desktop's Part A: `packages/core`'s `PracticeSessionController` already composes `PlayingPracticeMachine` + `DrillingMachine` into "the single state machine a UI actually drives." Wiring that in now means Phase 7 (real Drilling UI, both platforms) only has to change what `computeViewState()`'s `'drilling'` branch produces (and what `PlayingPracticeScreen.tsx`'s `SessionPanel` renders for it), not replace the integration itself.

**What Phase 6 Part B left for `'drilling'` (historical — superseded by Phase 7 Part B, see that section below):** while the session was in drilling mode, the emitted view state carried `mode: 'drilling'`, a `targetNoteLabel`, and nothing else active — `progressText`, `liveFeedbackText`, and `dwellFraction` were all `undefined` and `showGiveUpButton` was `false`. `PlayingPracticeScreen.tsx` rendered this as the same large target-note text Playing Practice uses, plus a small uppercase "Drilling" label — no live hearing-feedback line, no dwell-progress bar, no "Nice!" flash, and no skip button. The automatic attempt-timeout (`PracticeAttemptTracker`/`DEFAULT_ATTEMPT_TIMEOUT_MS`, `packages/core`) still functioned underneath even with the button hidden, so a stuck drilling rep was never _unrecoverable_, just without a manual escape hatch or visible progress. `DrillingMachine`'s own `consecutiveCorrect`/`attemptsUsed` counters and its `skip()` escape hatch were already fully implemented and tested in `packages/core` (Phase 2) — only the UI chrome for them was left for Phase 7 Part B. **See "Phase 7 Part B: Drilling UI" below for what replaced this placeholder.**

### What it looks like

A second screen (`PlayingPracticeScreen`, hidden until its tab is active — see "Mode switcher" above):

1. **Header** — a plain "Playing Practice" title (no debug toggle; Playing Practice has no debug panel of its own, mirroring desktop, which shares Finger Tuner's single debug panel rather than duplicating one).
2. **Sequence settings** (config phase, shown before "Start sequence" is pressed) — directly surfaces `packages/core`'s `SequenceGeneratorConfig`, porting the _concept_ of desktop's `<details>` panel with RN-idiomatic controls rather than a literal translation:

   - **Pattern** / **Direction**: a small `SegmentedControl` of Pressable buttons each (open strings/stepwise-first-position/one-octave-scale; ascending/descending/both) — the RN analogue of desktop's `<select>`s, since RN has no native dropdown primitive worth reaching for here.
   - **Min/max frequency (Hz)**: two `TextInput`s (`keyboardType="numeric"`), holding raw text exactly like desktop's `<input type="number">`'s own `.value` — parsed via `Number(...)` only when actually generating a sequence, never fought over by the controller while the user is mid-edit.
   - A live preview line (note count + first few labels, or a friendly message for a config that produces zero notes, or the `RangeError` message for a structurally invalid one), updating on every control change — same three-way outcome as desktop's `updatePreview()`.

**Two deliberate simplifications versus desktop's literal markup**, both visual-design judgment calls within this phase's explicit latitude to "port the concept, not the code," neither affecting scoring/domain logic at all:

- **No `<details>`-equivalent collapsible config panel.** Desktop's HTML uses a native `<details>` element the user can reopen at any time (even mid-session, which — as an incidental quirk of that markup rather than an intentional feature — shows both the config and session views simultaneously). This app instead treats config and session as two simple, mutually exclusive screens: pressing "Start sequence" switches to the session view, and the _only_ way back to config is the complete screen's explicit "Start a new sequence" button — there is no mid-session "cancel"/"edit settings" control. This matches desktop's actual _intended_ flow (nothing in `apps/desktop/CLAUDE.md` documents the mid-session reopen as deliberate), just without the `<details>` element's incidental always-reachable side door.
- **`PillButton` is duplicated locally in `PlayingPracticeScreen.tsx`**, not imported from `FingerTunerScreen.tsx` (which has its own, unexported, near-identical component) or extracted into a new shared file. This follows the same "small enough that a shared export isn't worth the cross-file coupling" precedent `apps/desktop/src/playing-practice-ui.ts` already established for its own `formatSignedCents` (also duplicated here rather than imported from `src/tuner/tuner-view-model.ts`'s `formatCents`) — and keeps this phase's change surface to exactly "add the new mode," with zero risk to Finger Tuner's already-verified screen.

## Phase 7 Part B: Drilling UI

### What it looks like

Drilling reuses the same session view Playing Practice renders into (no separate screen), exactly mirroring desktop's own "reads as a natural extension, not a different UI" design:

### View-state shape changes (this app's own internal contract, not `packages/core`'s)

Since this app has no DOM to leave fields "just not updated" on during a pause (see `playing-practice-controller.ts`'s own doc comment on the `currentMode`/`currentProgressText`/`currentTargetNoteLabel` cache), `PlayingPracticeSessionViewState`'s `'active'` variant needed real shape changes to carry Drilling's new chrome — this is `apps/mobile`'s own internal view-state type (defined and consumed entirely within this app), not a `packages/core` API, so widening it here is a normal, contained refactor, not the kind of cross-package API change Hard Rule 3 asks to be flagged:

### A real, narrow bug found and fixed while porting: `giveUp()`'s timestamp domain

Phase 6 Part B's `giveUp()` used `Date.now()` for the timestamp it feeds into `applyResult()`, with a doc comment explaining why that was safe at the time: a manual give-up always resolves to a failure, and in Phase 6 a failure never scheduled a pause (only a success did), so the timestamp value was never actually read on that path. Phase 7 invalidates that reasoning: a failure that ends a drill via the attempt cap **does** now schedule a banner pause (`showDrillEndBanner`, via `pauseUntilMs`), compared against `handleAnalysisFrame`'s `performance.now()`-based timestamps elsewhere in this same pipeline. Feeding `Date.now()` (Unix-epoch-scale, ~10^12) into that comparison against `performance.now()`-based values (process-relative, much smaller) would make `pauseUntilMs` permanently unreachable — `timestampMs < pauseUntilMs` would always be true — silently stranding the "Moving on" banner on screen forever. This specific path isn't reachable through this app's own UI today (the give-up button is hidden while drilling, so `giveUp()` can never itself observe `stateBefore.mode === 'drilling'`), but the method has no way to enforce that invariant from the caller's side, so it was fixed at the source rather than left as a latent trap: `giveUp()` now uses `performance.now()`, confirmed available as a global in both this app's Node/Vitest test environment (checked directly: `node -v` reports v25.9.0, and `typeof performance.now === 'function'`) and at runtime (Hermes/React Native; `mic-capture-controller.ts` already relies on it unguarded) — matching `handleAnalysisFrame`'s own domain exactly, and matching `apps/desktop`'s `giveUpBtn` click handler, which always used `performance.now()` for the identical reason. See `playing-practice-controller.ts`'s own `giveUp()` doc comment for the full writeup.

### File picking: `expo-file-system`, not a separate picker module

SDK 57's `expo-file-system` has its own picker (`File.pickFileAsync()`, result `{ canceled, result: File }`) and `File.text()`, so `abc-file-picker.ts` uses only that -- no `expo-document-picker`. **Play-along panel** (`PlayAlongPanel.tsx`): a header (tempo text `♩ = 92`, **Stop**), the progress text ("Count-in", "Pickup", "Bar 3 of 16"), **beat dots** (one per beat of the bar; the downbeat larger, the sounding beat filled -- blue, orange on the downbeat -- and swelling for the first third of its beat), then the stage: Letters shows the big name of the note the player is on (blue while due, green once hit, red once missed) and "Next: ..."; Staff shows the **notated score window starting at the current bar** (`ScoreView`), every note coloured by state (due blue, hit green, missed red, pending ink) with a thin **playhead**. Well played!", and the buttons **Play again** / **Practice missed notes** (only if something was missed) / **Change settings**. **Practice missed notes** starts a Wait-for-me session over just those notes; when it ends the complete screen offers **Play along again** and **Change settings**.

**Wait for me + Staff on an ABC piece** now draws the same notated score window, starting at the _target's bar_, with the target note blue (Drilling follows the drilled note; the bar window moves on when the target crosses a bar line). ### How it is wired

```
AbcPracticeScreen --- import --> TempoSettings (core describeTempoSettings via controller)
       |            -- play-along --> PlayAlongPanel --polls--> controller.getPlayAlongView()
       |            -- session  --> SessionPanel (PracticeParts) --> ScoreView | StaffView
AbcPracticeController (headless)
   settings: style, countInBars, tempoOverride            frames: handleAnalysisFrame
   play-along: PlayAlongRunner (core) ------------------------> runner.handleFrame (no React state)
   wait:       PracticeSessionRunner.begin(notes, {key, piece})
   missed:     PracticeSessionRunner.begin(notesAtIndices(...), {key})   (no piece: no score window)
```

- **`AbcPracticeController`** (`abc-practice-controller.ts`, headless, RN-import-free) owns: `setStyle` / `setCountIn` / `setTempo(bpm)` / `resetTempo()`; `start()` (style decides); `stopPlayAlong()`, `playAgain()`, `practiceMissedNotes()`, `changeSettings()` (= `restart()`); `getPlayAlongView()`; and forwards every frame to whichever of the run / the Wait-for-me session is active. Its view state gained `style`, `countInBars`, `tempo` (core's `TempoSettings` + range + `source` + `countInBeats`) on the import screen, a `'play-along'` phase carrying only the _static_ run info (`runId`, `piece`, `tempoBpm`, `countInBeats`), and `missedNotesOnly` on the session phase. The constructor takes `{ nowMs }` (default `performance.now()`) for tests.
- **Tempo** is a single number the controller keeps in the piece's own beat unit and hands to the plan (which scales every tempo mark in the piece by the same ratio); **the file's text is never modified** (it is not even kept after parsing). It resets to the written tempo when the file, the _selected tune_ or the _transposition_ changes (re-selecting the same tune / transposition does not reset it; style and count-in are preferences and are kept). All clamping (20..300, whole numbers), the percentage and the hint wording come from core's `describeTempoSettings` / `clampTempoBpm` -- nothing is re-derived here. One extra rule: an _untouched_ tempo is played exactly as written (92.5 stays 92.5 although the field shows 93), unless the file's tempo is outside the allowed range, in which case the clamped number is used.
- **Frames never reach React in play-along.** `App.tsx`'s `onAnalysis` already calls `abcControllerRef.current?.handleAnalysisFrame(...)` per hop; in play-along that feeds `PlayAlongRunner.handleFrame` and returns. `onChange` fires only on user actions (start, stop, play again, ...). `PlayAlongPanel` polls `getPlayAlongView()` every 33 ms **only while a run is live and the ABC tab is the visible one** (`visible` prop = `mode === 'abc'`; the run itself is clock-driven, so a hidden tab misses nothing and the next poll catches up immediately), calls `setState` only when `nextDisplayMark` (`play-along-view-state.ts`, pure and tested) says something visible changed -- the beat, the cue, a note resolving, the score window moving to another bar, the signal banner, the results; the flickering feedback text and dwell bar at most every 100 ms and the dwell bar in 2% steps -- and stops polling by itself once the run is `finished`. The score drawing is memoized (each primitive is its own memoized element keyed on its colour, so a note turning green re-renders only that note), and the **playhead is a separate tiny component** fed straight from the poll that moves in half-pixel steps, so moving it never re-renders the notation. The panel is keyed by `runId`, so "Play again" mounts a fresh one.
- **Leaving the app ends a live run** (`App.tsx`'s `AppState` handler calls `stopPlayAlong()` next to `pauseForBackground()`): a timed exercise cannot be paused, so the player comes back to the results of what was played (or the settings, if nothing had been judged yet), not to a run that carried on without them.
- **Stop** shows the results of the notes judged so far (the rest "not reached"); if _nothing_ had been judged yet (stopped in the count-in) it goes straight back to the settings instead of a "0 of 16" card.

### Clocks

The run's display time (count-in number, beat, playhead, `signalLost`) comes from `nowMs` = `performance.now()`; its scoring time comes from the frame timestamps, which `App.tsx` also takes from `performance.now()` per hop, so both are one clock domain. This is the same clock Playing Practice already uses. **Do not stamp frames with `Date.now()`.**

### No audible click on mobile (deliberate)

The runner is created **without** a `click`, so a mobile run is silent: you see the beat (dots, count-in number, the flashing downbeat), you do not hear it. `MicCaptureController.configureSession` sets the iOS audio session to `record` + `measurement`; playing a click needs `playAndRecord`, which could change how the instrument input is captured -- and pitch correctness is the app's first priority -- and it cannot be tried here (no device). So the audio session is untouched, and the tempo panel says "Visual beat only on mobile for now". To add a click later: pass `click: (atMs, accent) => ...` when `AbcPracticeController.startPlayAlong` builds the runner (core's `ClickScheduler` already does the look-ahead scheduling), switch the session category, set `PlayAlongConfig.extraLatencyMs` to the output latency, and re-check the input first.

### Judgment calls (flagged so they are not silently "fixed")

- **Default style is Play along**, count-in one bar. The existing untimed flow is the second option, "Wait for me".
- **The big number is a countdown** (`countInRemaining`) rather than the beat in the bar, matching desktop; the beat dots show the bar position.
- **Bar-by-bar window**: the score starts at the current bar. On a phone core's `sizeScore` (staff space >= 10 px) fits one bar of four quarter notes (two or three bars of sixteenths); the notation jumps at each bar line.
- **A hidden tab pauses redraws, not the run**; **leaving the app stops it** (above).
- **Practice missed notes** has no score window (the notes are not the piece in order, so "the target's bar" would show the wrong neighbours); the Staff display there is the older lookahead staff, which already draws flats from the written spelling, and its Letters labels are flat-aware (via the key), which goes slightly beyond "only when a piece is given".
- **The detection lag is core's default (60 ms), not measured on a phone.** Mobile's `onAudioReady` callback adds JS-thread/buffer latency that desktop's worklet does not, so timing offsets on a real device may read late; `PlayAlongConfig.detectionLagMs` / `extraLatencyMs` is the knob and is not wired to anything yet.
- **The tempo field commits when editing ends** (blur / submit), not per keystroke, and the scroll view does not use `keyboardShouldPersistTaps`: with the number pad up, the first tap elsewhere dismisses the keyboard and commits the number, the second tap acts.
- **The existing Wait-for-me tests now choose the style explicitly** (`setStyle('wait')`), because the default became Play along, and one expectation changed on purpose: the "Next:" line of a B-flat tune reads "E♭5", not "D#5".

### Core API notes (for whoever maintains `packages/core`)

- `layoutScore`/`sizeScore`/`barIndexAtWhole` and the tempo model were not exported from `index.ts` when this work started; they are now.
- `ScoreLayout.viewBox` reserves a fixed ~13 staff spaces of height (about 130 px on a phone), of which roughly 50 px sit above the staff, so a window of a low-register piece shows blank space over the staff. Phase 8 deliberately chose the privacy-safer plan interpretation — auto-pause on background/inactive, then explicit Resume on return unless the OS itself clearly handed the session back while still foregrounded — rather than enabling background recording or a foreground service.
- The Phase 4b Tuneo-style native-TurboModule fallback — conditional on the go/no-go checkpoint below failing; not started, and shouldn't be, until that checkpoint actually runs on a real device.
- True Android input-device selection — blocked on `react-native-audio-api`'s own current platform support (see "External audio interface" above), not something this app's own code can add.
- An Android-side AGC/noise-suppression control — blocked on the same library not currently exposing one (see "Known correctness gap" above).
